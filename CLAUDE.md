# null — как здесь работать

Личный статичный архив: 134 объекта, ~117 эссе, 36 визуализаций. Без сборки,
без фреймворка. GitHub Pages деплоится из `main`, поэтому пуш в main — это
правка сразу в прод.

## Порядок при любой правке *.html

```
scripts/update_meta.py            ─┐
scripts/update_counts.py           │  до коммита
scripts/update_reading_time.py    ─┘
git commit
scripts/generate_sitemap.py          после коммита: берёт lastmod из git
git commit --amend
scripts/preflight.py                 блокеров быть не должно
git push
```

Карту надо перегенерировать после **любого** коммита, меняющего `*.html`, а не
только после новой страницы: `lastmod` меняется от любой правки файла. Счётчики
в `essays/index.html` правятся руками, два числа на секцию.

## Откуда берётся работа

`audit/` — не свалка, а конвейер. Источники в порядке приоритета:

| файл | что там |
|---|---|
| `audit/revision-queue.md` | **канон.** Очередь доработки со статусами ☐ не прочитано · ◐ прочитано · ☑ исправлено-закоммичено |
| `audit/objects-flags.md` | механические флаги по объектам, генерируется `audit/collect_objects.py` |
| `audit/essays-flags.md` | то же по эссе, генерируется `audit/collect_metrics.py` |
| `audit/factual-worklist.md` | даты, атрибуции, «впервые» — только ручная и веб-проверка |
| `audit/priority.md` | чем заняться раньше |

Файлы `objects-*.md`, `essays-*.md`, `*-metrics.csv` — **генерируемые**. Правки
вносить в скрипт, а не в них: следующий прогон затрёт. Перегонять их надо
**после** правки HTML, иначе в коммит попадёт снимок доправочного состояния.

Отдельно приходят задания вида `null-fix-<дата>-<slug>.md` — разбор одной
сущности от запланированного аудита. У них своя структура: разделы A, B и C.

## Два класса правок, и их нельзя путать

**Раздел A — применять.** Проверяемое: фактическая ошибка с источником,
арифметика, простаивающая ссылка, метаданные. Есть внешнее подтверждение или
расчёт — применяй, отмечай ☑ с хешем коммита.

**Раздел B — не применять.** Ритм, регистр, повторы, антитеза «не X, а Y»,
ударные концовки. Это авторский голос, а не дефект. Смысл аудита в том, что
тексты местами читаются как нейрогенерация; если их будет переписывать модель,
следы не исчезнут, а станут ровнее и мертвее. По разделу B можно предложить
варианты в обсуждении — но не править файл без явного решения автора.

**Раздел C — общесайтовое.** Заводить отдельной задачей, не смешивать с правкой
одной страницы.

## Чего здесь не делают

- Не переписывают прозу без спроса — см. выше.
- Не заводят второй счётчик слов. Он один, живёт в
  `scripts/update_reading_time.py`, и `audit/collect_objects.py` импортирует
  его оттуда — тем же приёмом, каким `update_meta.py` берёт построение URL из
  `generate_sitemap.py`. Два счётчика уже разъезжались однажды и держали пять
  объектов в вечных ложных срабатываниях.
- Не считают слова по одним `<p>`: у объектов половина текста в таблицах и
  врезках. Считается видимый текст в `<main>` минус обвязка (breadcrumb,
  related, backlinks, topbar, footer), причём **вместе с самой меткой**:
  авторские числа посчитаны с ней, и без неё весь корпус уезжает на десяток
  вниз. Проверочные точки — `cantor` 420, `loss-aversion` 400, `demoivre` 500,
  `1729` 480, `godel` 420: счёт обязан сходиться до единицы.
- Не правят генерируемые файлы руками.
- Не пушат в `main` напрямую, если правок больше одной строки: PR, `preflight`
  в CI, потом мерж.

## Конвенции текста

- Лид (`p.essay-lead`) — со строчной буквы после точек. Это приём, а не опечатка,
  он выдержан по всей картотеке.
- Метка `div.essay-label`: слова округляются до десятка, минуты ≈ `ceil(слова / 125)`.
- Заголовки строчные — `preflight.py` это проверяет.
